# Modern file sync alternatives in Rust and Go

> Research date: 2026-09-20
> Query: modern alternatives to Syncthing, and ways to build a faster Syncthing-like system in Rust or Go

## Executive take

Syncthing is still a strong baseline for decentralized folder replication. A replacement only wins by choosing a narrower target:

- **Developer workspaces:** Mutagen. It uses a local agent model and is optimized for low-latency file exchange between hosts and containers.
- **Cloud-backed collaboration:** Seafile or Nextcloud. These trade Syncthing's peer-to-peer simplicity for centralized indexing, sharing, web access, and server-side storage.
- **Content-addressed or deduplicated sync:** Copia is worth studying as a Rust design reference.
- **Cross-platform distributed storage:** Spacedrive is a broader Rust project, closer to a distributed file manager than a direct Syncthing replacement.
- **Experimental Rust-native direction:** `syncthing-rust`, K2 Network, SOVTHING, and `rasync` show possible building blocks, but they need maturity and benchmark review before production use.

The best product opportunity is not a general Syncthing clone. It is a focused sync engine with faster change detection, better large-file handling, resumable transfers, and an optional relay or coordination service.

## Existing alternatives

### Mutagen

Mutagen targets real-time file synchronization for development workflows. It is a strong reference for a session-oriented architecture, especially when syncing a laptop with a remote host, container, or virtual machine. It is less suitable as a general always-on personal folder mesh.

### Seafile

Seafile uses a server-backed model with block-level storage and deduplication. It is a better fit when users need a central source of truth, web access, multi-user sharing, permissions, and efficient storage of repeated content. It gives up Syncthing's fully peer-to-peer model.

### Nextcloud

Nextcloud is a collaboration platform with file sync as one feature. It fits teams that need accounts, sharing, web editing, calendars, and integrations. It has a larger operational surface and usually more overhead than a focused sync daemon.

### Resilio Sync

Resilio is a mature peer-to-peer synchronization product built around BitTorrent-style transfer ideas. It is a useful performance benchmark for large files and many peers, but its closed-source model limits reuse of its implementation.

### Unison

Unison is reliable for two-way synchronization and conflict handling. It is a useful reference for explicit replica state and deterministic conflict behavior, but its workflow is less seamless than an always-on daemon.

### Spacedrive

Spacedrive is a Rust-based distributed file manager. Its architecture is broader than folder sync, so it is useful for studying Rust cross-platform design, metadata indexing, and distributed storage concepts rather than copying as a direct Syncthing alternative.

### Copia

Copia is a Rust project focused on content-addressed data and deduplication. It is relevant to a faster design that hashes file chunks, stores immutable objects, and transfers only missing blocks. Check project maturity and current protocol guarantees before using it as a dependency.

### Experimental projects

- `juice094/syncthing-rust`: a direct Rust implementation attempt and useful protocol study.
- K2 Network: a distributed networking project with possible relevance to peer discovery and transport.
- SOVTHING: an experimental Syncthing-related project.
- `librats/rasync`: a Rust synchronization project using modern networking ideas.

Treat these as research inputs, not production recommendations, until they pass independent interoperability, security, and failure-recovery tests.

## What could be faster than Syncthing

### 1. Separate discovery, metadata, and data paths

Use a small coordination layer for device identity, peer discovery, folder membership, and announcements. Keep file data transfers direct between peers whenever possible. This avoids forcing every peer to maintain a large global state model.

### 2. Use a content-defined chunker

Fixed-size blocks are simple but perform poorly when bytes are inserted near the start of a large file. Content-defined chunking keeps most chunk boundaries stable after insertions. Combine it with a strong hash such as BLAKE3.

Recommended starting point:

- Fast path: whole-file metadata check using size, mtime, inode or file ID, and a cheap sample hash.
- Changed file: content-defined chunking.
- Transfer: missing chunk IDs only.
- Storage: chunk cache with reference counts and garbage collection.

### 3. Use QUIC for transport

QUIC gives encrypted streams, multiplexing, connection migration, and better behavior than a hand-rolled TCP protocol when several files transfer at once. Rust options include Quinn. Go options include `quic-go`.

Use separate logical streams for:

- control and capability negotiation
- directory metadata
- chunk requests
- chunk payloads
- acknowledgements and repair

### 4. Make scanning event-driven

Use filesystem notifications for immediate change detection, then run periodic reconciliation scans to catch missed events. Rust has `notify`; Go has `fsnotify`.

Do not trust events as the only source of truth. Editors often use rename-and-replace patterns, and network filesystems can drop or reorder notifications.

### 5. Use an append-only change journal

Each replica should record changes as a journal with a monotonic local sequence. Peers exchange compact watermarks before requesting full metadata. This reduces repeated directory walks and makes reconnects cheaper.

For multi-device causality, use version vectors or dotted version vectors. Do not use wall-clock timestamps as the conflict authority.

### 6. Pipeline transfers

A high-throughput peer should read, hash, compress when useful, encrypt, and send chunks in a pipeline. Limit memory with bounded queues. Use backpressure per peer and per folder.

Large-file performance depends more on disk scheduling, chunk cache hits, and parallelism than on the language alone.

### 7. Add adaptive transport behavior

Measure RTT, loss, throughput, disk read speed, and CPU cost. Choose parallel stream count and chunk size from those measurements. A fixed worker count will underperform across local LAN, Wi-Fi, WAN, and relay paths.

### 8. Treat relays as optional

Direct connections should be preferred. A relay should forward encrypted payloads without seeing file contents. Use a small rendezvous service for discovery and NAT traversal, but keep the system usable with self-hosted discovery or static peer addresses.

## Rust versus Go

### Rust

Best fit when the client needs low memory use, predictable CPU cost, a reusable protocol library, and tight control over concurrent state. Rust is a good choice for a cross-platform daemon that runs continuously on laptops, phones, NAS devices, and servers.

Likely components:

- Tokio for async runtime
- Quinn for QUIC
- BLAKE3 for hashing
- `notify` for filesystem events
- SQLite or redb for local state
- serde for protocol structures
- tracing for diagnostics

Main cost: longer development time and more complex platform integration.

### Go

Best fit when fast delivery, easy operations, and a small team matter most. Go's networking and concurrency model are strong for a daemon and coordination service. Cross-compiling is simple, and profiling is straightforward.

Likely components:

- `quic-go` for QUIC
- `fsnotify` for filesystem events
- BLAKE3 Go implementation
- SQLite, Pebble, or Badger for local state
- protobuf or a versioned binary protocol
- OpenTelemetry or structured logging

Main cost: higher baseline memory use and less compile-time protection for complex shared state.

### Practical recommendation

Use Rust for the sync core if the goal is a durable Syncthing successor. Use Go for Syncthis because fast delivery, simple operations, and a LAN-first product are the current priorities. Another practical split is a Rust client core with a Go control plane, but this adds deployment and protocol complexity.

## Proposed architecture for a better Syncthing-like system

### Components

1. **Agent:** runs on each device, owns local folders and the change journal.
2. **Coordinator:** optional service for identity, discovery, folder membership, and relay allocation.
3. **Peer transport:** direct QUIC first, encrypted relay second.
4. **Metadata store:** local embedded database containing file manifests, chunk references, version vectors, and transfer state.
5. **Chunk store:** content-addressed local cache with quotas and garbage collection.
6. **Conflict engine:** explicit policy for keep-both, last-writer, manual review, or application-specific merge.
7. **CLI and UI:** status, pause, bandwidth limits, conflict review, device approval, and audit logs.

### Sync protocol flow

1. Detect a filesystem event.
2. Normalize the path and classify the operation.
3. Append the operation to the local journal.
4. Reconcile the affected file and produce a manifest.
5. Announce the manifest root and journal watermark to peers.
6. Exchange version vectors and manifest differences.
7. Request missing chunks.
8. Stream chunks over parallel QUIC streams.
9. Verify each chunk and final file hash.
10. Atomically install the file and record the acknowledgement.
11. Run periodic reconciliation to repair missed events or corrupted state.

### MVP scope

Start with two devices on the same LAN:

- one-way and two-way folder sync
- BLAKE3 whole-file hashes first
- fixed-size chunks before content-defined chunks
- QUIC with mutual device keys
- SQLite metadata
- filesystem event watcher plus periodic scan
- keep-both conflict policy
- resumable transfers
- bandwidth limits
- CLI status and logs

Add NAT traversal, relay support, content-defined chunking, multi-device version vectors, mobile clients, and a web UI only after the LAN protocol survives crash and power-loss tests.

## Benchmark plan

Compare against Syncthing, Mutagen, and one server-backed option using the same hardware and files:

- initial sync of 1 GiB, 10 GiB, and 100 GiB
- 10,000 small files
- one 50 GiB file with a 1 MiB insertion near the beginning
- rename storms and editor save patterns
- LAN, Wi-Fi, 100 ms WAN, and relay paths
- interrupted transfer and process restart
- simultaneous edits and conflict recovery
- CPU time, peak RSS, disk writes, network bytes, time to convergence
- battery impact on a laptop

The key metric is not peak throughput alone. Measure time from local change to verified convergence and the bytes transferred after small edits.

## Main risks

- Filesystem semantics differ across Linux, macOS, Windows, and mobile platforms.
- Conflict resolution is a data-loss risk and needs conservative defaults.
- A content-addressed store needs secure garbage collection and quota handling.
- Device identity and key rotation need a clear recovery path.
- Relay and discovery services can become a privacy or availability dependency.
- Faster hashing does not help if the design still scans every file on every cycle.

## Architecture objective

Syncthis must begin with a solid, extensible architecture rather than a throwaway implementation. The design should support new transports, storage engines, user interfaces, operating systems, discovery methods, and sync policies without changing the core synchronization rules.

Use ports and adapters with a strong domain model:

- **Domain core:** file versions, replicas, devices, folders, manifests, chunks, operations, journals, conflicts, sync sessions, and policies.
- **Application use cases:** pair devices, add folders, scan, compare manifests, plan changes, transfer data, apply changes, resolve conflicts, pause and resume, repair state, and report status.
- **Ports:** filesystem, metadata store, content store, clock, peer discovery, transport, device identity, configuration, event stream, logging, and user interface.
- **Adapters:** local filesystem, SQLite, Tailscale peer discovery, TCP or QUIC transport, CLI, TUI, JSON output, and system service integration.

The domain and application layers must not import Tailscale, SQLite, `fsnotify`, Bubble Tea, Cobra, or operating-system-specific code. Adapters depend on ports. The composition root wires concrete adapters to the application.

The architecture must make these future changes possible without rewriting the domain core:

- Replace SQLite with another metadata store.
- Add content-defined chunking and deduplication.
- Add LAN discovery, hosted discovery, or another network transport.
- Add mobile or web clients.
- Add a Rust implementation of the protocol or domain logic.
- Add new conflict policies and file synchronization modes.
- Add another interactive or graphical interface.

### Implementation decision: Go

Syncthis will be written in Go. Go is an implementation choice, not an excuse to weaken the architecture. Keep the protocol and local state format documented so a Rust implementation remains possible later, but optimize the initial release for fast delivery and iteration while preserving the domain boundaries.

### Product objective

Validate personal file synchronization across two Tailscale-connected devices. The first release must prove peer pairing, folder watching, file transfer, interruption recovery, conflict visibility, CLI automation, and interactive terminal operation before broader platform or performance work.

### Initial release scope

**Include:**

- Go implementation.
- Linux-first support.
- Two personal devices.
- Tailscale hostname or IP pairing.
- Tailscale-only listener by default.
- One or more synced folders.
- Arbitrary file types.
- One-way replication first, followed by two-way sync in the same release.
- Filesystem events plus periodic reconciliation scans.
- Whole-file BLAKE3 hashes.
- Fixed-size chunks for resumable transfers.
- Keep-both conflict handling.
- CLI with JSON output.
- Interactive TUI.
- SQLite local state.
- Reconnect after process, network, and Tailscale interruptions.

**Excluded from the initial release:**

- Mobile clients.
- Three-way merging.
- Content-defined chunking.
- Cross-file deduplication.
- Public relays.
- Hosted accounts.
- Team sharing.
- Custom VPN functionality.
- Complex permissions.
- Automatic binary merging.
- Windows and macOS packaging until the workflow is validated.

### Initial release success metrics

- Pair two Tailscale devices through the CLI in under two minutes.
- Complete setup through the TUI without reading source code.
- Correctly sync a 10,000-file test folder.
- Detect ordinary changes within two seconds.
- Resume an interrupted 10 GB transfer without retransmitting verified chunks.
- Never silently overwrite a conflicting file.
- Reconnect after a Tailscale restart without manual database repair.
- Stay below 150 MB idle memory on the reference Linux device.
- Produce stable JSON status suitable for scripts.
- Record convergence time, bytes transferred, CPU, memory, disk writes, and recovery events for every test.

### Initial Go stack

- Go standard library for process, filesystem, and networking support.
- `fsnotify` for filesystem events.
- BLAKE3 implementation for hashing.
- SQLite for local metadata, journal, transfer state, and conflicts.
- Cobra or a similarly stable CLI framework.
- Bubble Tea with Lip Gloss for the interactive terminal UI.
- Structured logging with stable event fields.

The first transport should be a simple authenticated stream over Tailscale. Benchmark TCP and QUIC before selecting a more complex transport. Tailscale already supplies encrypted network reachability, so Syncthis should not build a custom VPN or public relay.

### Delivery milestones

1. Local folder scanner, metadata store, ignore rules, and CLI status.
2. Tailscale peer pairing and authenticated health check.
3. One-way file transfer with fixed-size chunks and resume.
4. Interactive TUI for setup, status, pause, resume, and repair.
5. Two-way sync with keep-both conflicts.
6. Failure testing, benchmark corpus, and comparison against Syncthing.

### Future implementation review

A future Rust version is justified only if benchmark or operational evidence shows that Go cannot meet the target memory, throughput, latency, or reliability goals. Any rewrite requires measured justification, a migration plan, and compatibility tests.

## Product direction: Tailscale-first P2P sync

The primary network goal is direct peer-to-peer synchronization over the user's existing Tailscale network. The system should not require a public coordinator, port forwarding, or a vendor relay for the normal path.

### Network requirements

- Discover peers through Tailscale device identity, MagicDNS names, or explicit Tailscale IPs.
- Prefer direct Tailscale paths and let Tailscale handle NAT traversal and WireGuard encryption.
- Bind the sync listener to the Tailscale interface by default, not the public interface.
- Support explicit peer addresses for hosts without MagicDNS.
- Verify the expected Tailscale node identity before accepting a device.
- Support Tailscale ACLs as the first access-control boundary.
- Expose the sync service on a configurable port.
- Provide a connectivity diagnostic that reports interface, peer address, route, latency, MTU, and connection failure reason.
- Work across Linux, macOS, Windows, NAS hosts, containers, and headless servers where Tailscale runs.
- Support a local LAN fallback only when explicitly enabled.
- Keep public relays, hosted discovery, and internet exposure out of v1.

### Tailscale-focused commands

```bash
docsync network tailscale detect
docsync network peers
docsync peer add nas.tailnet-name.ts.net --verify
docsync peer test nas.tailnet-name.ts.net
docsync daemon run --interface tailscale0
docsync status --network --json
```

Interactive mode should show each peer's Tailscale hostname, tailnet IP, online state, direct-path status, latency, and last successful transfer. It should explain when traffic is direct, DERP-relayed by Tailscale, blocked by ACLs, or failing because a node is offline.

### Tailscale security model

Tailscale provides encrypted transport, but the sync protocol should still authenticate devices at the application layer. Pairing must require explicit approval and produce a device key or certificate. Folder permissions must be separate from network reachability.

The daemon must never expose the sync API on `0.0.0.0` by default. Admin operations should be local-only or require an authenticated Tailscale peer. Logs should avoid leaking file contents and should identify peers by stable device ID.

### Success targets for the Tailscale path

- Pair two already-connected Tailscale devices from the CLI in under two minutes.
- Start syncing without opening firewall ports or creating a vendor account.
- Detect a direct Tailscale path before the first transfer.
- Propagate an ordinary document change in under one second when both devices are online and the path is healthy.
- Resume a transfer after a Tailscale disconnect without restarting the file.
- Report whether a transfer used a direct path or Tailscale DERP within the CLI and TUI.
- Keep the sync daemon usable when the Tailscale agent restarts or the device changes networks.
- Allow the user to restrict each folder to an explicit set of approved Tailscale device IDs.

### Revised v1 boundary

V1 is a general file sync daemon for two or more devices connected through Tailscale. It includes arbitrary file types, one-way and two-way folders, resumable transfers, conflict-safe behavior, CLI automation, and an interactive TUI. It does not include a public relay, hosted account system, internet-wide peer discovery, or a custom VPN. Those are unnecessary for the first target environment.

## Phased delivery plan

### Phase 0: Test harness and baseline

**Goal:** Establish measurable comparisons before building the replacement.

**Scope:**

- Build a repeatable fixture generator for small files, large files, deep trees, renames, deletes, binary files, and editor-style saves.
- Measure Syncthing and Obsidian Sync where available.
- Record convergence time, bytes transferred, CPU, memory, disk writes, and behavior after interruption.
- Define the document and arbitrary-file test corpus.

**Exit metrics:**

- At least 10 repeatable scenarios run from one command.
- Results stored as machine-readable JSON.
- Baseline measurements collected for LAN, Tailscale direct path, and Tailscale DERP path.
- Every later phase can run regression tests against the same corpus.

### Phase 1: Local single-device engine

**Goal:** Prove safe file observation, metadata, manifests, and local state without networking.

**Scope:**

- Add a folder and scan it.
- Detect creates, modifies, moves, and deletes.
- Handle arbitrary file names, hidden files, Unicode, empty directories, and symlinks by policy.
- Store file metadata and BLAKE3 hashes in an embedded database.
- Use filesystem events plus periodic reconciliation.
- Add ignore and include rules.
- Provide dry-run, status, rescan, and repair commands.

**Exit metrics:**

- Correctly classify at least 99.99% of generated filesystem operations.
- Reconcile 100,000 files without data loss or unbounded memory growth.
- Recover state after process kill and machine restart.
- Detect missed filesystem events during a reconciliation scan.
- Idle daemon memory stays below 100 MB on the reference desktop.

### Phase 2: Two-device Tailscale transfer

**Goal:** Transfer arbitrary files directly between two Tailscale-connected devices.

**Scope:**

- Device identity and explicit pairing.
- MagicDNS and Tailscale IP peer addresses.
- Listener bound to the Tailscale interface.
- Direct peer transport with encrypted sessions.
- File manifests and chunk requests.
- Resumable transfers.
- CLI and JSON status output.

**Exit metrics:**

- Pair two devices through the CLI in under two minutes.
- Complete a 10 GB transfer without exceeding 256 MB transfer memory.
- Resume an interrupted transfer with no retransmission of verified chunks.
- Reach at least 80% of measured baseline throughput on a Tailscale direct path.
- Report peer, path, latency, bytes sent, bytes remaining, and failure reason.
- No sync listener is exposed on a public interface by default.

### Phase 3: One-way and receive-only replication

**Goal:** Make backup and mirror workflows dependable before handling concurrent edits.

**Scope:**

- Send-only and receive-only folders.
- Read-only replicas.
- Delete propagation policies.
- Pause, resume, scheduled sync, bandwidth limits, and dry-run.
- Atomic destination writes.
- Crash-safe transfer journal.
- CLI configuration import and export.

**Exit metrics:**

- 1,000 interrupted transfer and restart cycles complete without corrupting files.
- SHA-256 or BLAKE3 verification matches the source for every completed file.
- A 1 TB mirror can resume after restart without a full re-scan transfer.
- 100% of destructive operations require an explicit configured policy.
- Scheduled and bandwidth-limited runs stay within 5% of configured limits.

### Phase 4: Two-way sync and conflict safety

**Goal:** Support offline edits without silent data loss.

**Scope:**

- Version vectors or equivalent causal state.
- Concurrent edit detection.
- Keep-both conflict handling.
- Rename versus delete handling.
- Case-only rename handling.
- Permission-only and symlink-target changes.
- Conflict list, show, resolve, and export commands.
- Optional three-way text merge. Never auto-merge binary files.

**Exit metrics:**

- Zero silent overwrites in the conflict test suite.
- 100% of generated divergent edits produce an explainable result.
- Every conflict records paths, devices, versions, hashes, and operations.
- 99.99% automatic convergence for non-conflicting changes.
- Conflict resolution works entirely through CLI and TUI.

### Phase 5: Performance and scale

**Goal:** Beat Obsidian Sync and Syncthing on the target document and Tailscale workloads.

**Scope:**

- Content-defined chunking for large files.
- Cross-file and cross-folder chunk deduplication.
- Parallel transfer pipelines with backpressure.
- Adaptive concurrency based on disk and network measurements.
- Rename detection without re-uploading content.
- Efficient journal watermarks instead of repeated full scans.

**Exit metrics:**

- Ordinary document change converges in under one second on a healthy Tailscale direct path.
- A 1 MiB insertion near the beginning of a 10 GB file transfers less than 2 MiB after warm cache.
- Rename of a 10 GB file transfers zero file payload bytes.
- 100,000-file vault status is available in under two seconds after an incremental change.
- Small document edits use at least 90% fewer network bytes than whole-file transfer.
- Beat the baseline on convergence time for at least 80% of the target corpus.

### Phase 6: Interactive terminal product

**Goal:** Make diagnosis and daily operation usable without a GUI.

**Scope:**

- Interactive TUI over the local daemon API.
- Guided initialization and pairing.
- Live device, folder, queue, path, and error views.
- Conflict review and version restore.
- Searchable event logs.
- Reattach after SSH or terminal disconnect.
- Every TUI action has a non-interactive CLI equivalent.

**Exit metrics:**

- New user can pair and sync a folder in under five minutes with no documentation.
- TUI can disconnect and reconnect without losing daemon work or state.
- 100% of supported TUI actions have documented CLI equivalents.
- JSON mode never emits ANSI or interactive prompts.
- All commands return documented stable exit codes.

### Phase 7: Multi-device hardening and release

**Goal:** Ship a reliable Tailscale-first general file sync system.

**Scope:**

- Three or more devices.
- Folder-level device authorization.
- Tailscale restart and network-change recovery.
- Direct versus DERP diagnostics.
- Upgrade and database migration handling.
- Security review and fuzz testing of protocol and path handling.
- Linux, macOS, Windows, NAS, container, and headless service packaging.

**Exit metrics:**

- 30-day soak test with no unrecovered sync failures.
- 10,000 forced network interruptions recover without manual database repair.
- No path traversal, arbitrary file write, or unauthorized-folder findings in security testing.
- Upgrade across two schema versions without losing sync state.
- Three-device convergence reaches 99.99% for non-conflicting test operations.
- Install, configure, and run as a system service on each launch platform.

## Bottom line

Build a Tailscale-first, Rust-based sync engine. Use Tailscale for encrypted network reachability, QUIC or another multiplexed transport over the Tailscale path, event-driven journals, BLAKE3 manifests, resumable chunk transfers, and direct peer connections. Keep application-level pairing, folder authorization, conflict safety, and audit logs inside the sync system.

The first release should not claim victory based on raw throughput alone. It should beat Obsidian Sync on CLI control, self-hosted P2P operation, explainable conflicts, recovery after interruption, and small-edit efficiency. Benchmark every claim against the Phase 0 corpus.
